# VPN-серверы блокируются в РФ: диагноз, временный фикс, план настоящего решения

Дата инцидента: 2026-07-28. Документ — полный контекст для передачи Claude в новой сессии без повторного объяснения. При покупке новых серверов — просто скинуть этот файл/текст целиком.

---

## 1. Симптом

Пользователи (и сам Максим) жаловались: в клиентском приложении (Happ/V2RayN) серверы «то не пингуются вообще, то пинг 500-600мс». Проблема касалась конкретно **Финляндии (fi-1), Нидерландов (nl-1) и Германии (DE)**. Германия-2 (de-2) работала, хоть и с повышенным пингом.

## 2. Что было проверено и ИСКЛЮЧЕНО как причина

- **Бэкенд/мониторинг говорил "всё живо"** — TLS-хендшейк проходит, xray слушает порт, панель 3X-UI отвечает, клиенты синхронизированы. Это вводило в заблуждение: мониторинг ходит с APP-сервера (Европа), а не из России — не видит блокировку по маршруту РФ→Европа.
- **Reality-конфиг (publicKey/shortId/serverNames) сверен между БД и реальными xray-конфигами на серверах — расхождений нет** (кроме одного мусорного поля, см. ниже).
- **Смена SNI с `rutube.ru` на `www.wildberries.ru` на fi и DE — НЕ ПОМОГЛА.** Это ключевой сигнал: раз смена домена-донора ничего не изменила, дело не в фингерпринте/SNI Reality.
- **Сам донор-домен НЕ заблокирован** — Максим лично проверил: `https://www.wildberries.ru` открывается в обычном браузере без VPN. Значит блокируется не домен-прикрытие, а нечто специфичное для наших серверов.

## 3. Настоящая причина (подтверждено)

**fi-1, nl-1 и DE физически хостятся у одного и того же реселлера — "Snowd Security OU"**, который перепродаёт IP-диапазоны крупного нидерландского хостера **HOSTKEY B.V. (ASN 57043)**, просто в разных их дата-центрах (Финляндия/Нидерланды/Германия):

| Сервер | IP | ASN / провайдер |
|---|---|---|
| fi-1 (Финляндия) | 89.125.53.210 | AS57043, Snowd Security OU → HOSTKEY B.V. |
| nl-1 (Нидерланды) | 78.17.16.183 | AS57043, Snowd Security OU → HOSTKEY B.V. |
| DE (Германия) | 78.17.56.109 | AS57043, Snowd Security OU → HOSTKEY B.V. |
| de-2 (Германия 2) | 89.127.203.48 | AS44051, Fornex Hosting S.L. — **другой, не связанный провайдер** |

Все три «умерших» сервера — на одном реселлере; единственный «живой» — на совсем другом. "Snowd Security" — бутиковый хостинг-бренд, который специально продаёт IP под VPN/прокси. Такие диапазоны — самая эффективная и частая мишень для блокировок в РФ: заблокировав один диапазон, гасишь разом десятки чужих VPN-сервисов, сидящих на том же реселлере.

**Вывод: блокировка идёт на уровне IP-диапазона хостинг-реселлера, а не по протоколу/порту/SNI.** Никакие правки конфига Reality на ЭТИХ ЖЕ IP это не обойдут.

## 4. Побочно найденные и исправленные баги (не главная причина, но реальные баги)

1. **`monitor_daemon.py`**, функция `check_tls_handshake()` — слала в TLS SNI голый IP-адрес сервера вместо настоящего домена-донора (`server['sni']`). Из-за этого мониторинг мог ложно показывать сервер как DOWN на серверах со строгой проверкой SNI. Исправлено: теперь передаётся `sni=server['sni']`.
2. **На fi было мусорное поле `dest`** в realitySettings, указывавшее на `www.bing.com`, тогда как `target`/`serverNames` указывали на другой домен (rutube.ru, затем wildberries.ru) — исторический рассинхрон. Поле `dest` убрано везде, используется только `target`.
3. Написан с нуля рабочий эндпоинт **`POST /admin-api/servers/<id>/apply_reality`** (кнопка «Применить SNI» в админке раньше вела в никуда — 404/405, отсюда «Ошибка сети»). Теперь реально пишет SNI/donor в inbound через 3X-UI API и рестартит xray.

## 5. Временный фикс, который сейчас держит сервис живым

На **de-2 (Fornex, не заблокирован)** настроен **прозрачный NAT-релей на уровне ядра** (iptables DNAT + MASQUERADE, `net.ipv4.ip_forward=1`):

- de2:9001 → форвардит на fi-1 (89.125.53.210:443)
- de2:9002 → форвардит на nl-1 (78.17.16.183:443)
- de2:9003 → форвардит на DE (78.17.56.109:443)
- собственный инбаунд de2 остался на 7443, не тронут

В таблице `servers` (Supabase) для fi-1/nl-1/DE изменены **только клиентские поля** `server_ip` → `89.127.203.48`, `server_port` → 9001/9002/9003. Поля `panel_url`/`panel_login`/`panel_password`/`inbound_id` **не тронуты** — админка по-прежнему управляет каждым сервером напрямую через его собственную 3X-UI панель.

**Почему это работает:** клиент подключается к IP Fornex (не заблокирован), de2 молча перебрасывает байты на настоящий fi/nl/DE. Шифрование Reality и выход в интернет как были на исходных серверах, так и остались — de2 просто труба. Гео (страна выхода в интернет) для пользователя не меняется.

**Почему это ВРЕМЕННО, не решение:**
- Single point of failure — если Fornex тоже попадёт под раздачу, упадут все 4 сервера разом, а не 3.
- de2 сейчас тащит трафик за 4 страны на одном канале/CPU — риск деградации и риск, что аномальный объём трафика сам привлечёт внимание блокировщиков.
- Заблокированные IP (fi/nl/DE) остаются заблокированными — мы их просто прячем за релеем, а не чиним.

## 6. Что нужно сделать для НАСТОЯЩЕГО, правильного решения

### 6.1. Купить новые VPS взамен fi-1, nl-1, DE

**Не тот же хостинг.** Критерий выбора провайдера:
- Крупный, универсальный, «скучный» хостинг с миллионами обычных клиентов — НЕ бутиковый VPN-резейл-бренд (как Snowd Security). Массовая блокировка диапазона такого провайдера — слишком большой collateral damage, провайдеры/РКН реже идут на это.
- Кандидаты: **Hetzner, OVH, Contabo, netcup, IONOS, Scaleway**. Fornex (где сидит de-2) тоже подходящий профиль — можно взять там ещё серверов, раз его пока не блокируют.

**Разнести 3 новых сервера по 2-3 РАЗНЫМ провайдерам**, не сажать все на один новый хостинг. Именно однородность (все три на одном ASN) стала причиной всего инцидента — при диверсификации следующая блокировка убьёт максимум один сервер, а не все три разом.

### 6.2. Что передать Claude, когда серверы куплены

Для каждого нового сервера:
- IP-адрес
- root-пароль (или добавленный SSH-ключ)
- какой сервер он заменяет (fi-1 / nl-1 / DE) или что это новая страна
- название провайдера (чтобы проверить реальную диверсификацию ASN)

Дальше Claude сам:
1. Развернёт 3X-UI + Reality через уже готовую автоматизацию `server_installer.py` (вызывается через `/admin-api/install_server` из панели)
2. Обновит `servers` в Supabase — новые `server_ip`/`server_port`/`panel_url`/`panel_login`/`panel_password` для замененных серверов, направит их напрямую (без релея)
3. **Разберёт временный релей на de2**: удалит iptables DNAT/MASQUERADE-правила (3 DNAT + 3 MASQUERADE для портов 9001-9003), при желании вернёт `net.ipv4.ip_forward=0`, снимет персистентность правил (`netfilter-persistent save` после очистки)
4. Проверит здоровье всех серверов через мониторинг и вживую (openssl s_client с правильным SNI)

### 6.3. Опционально, но правильно на будущее — CDN-фронтинг

Даже на новых «хороших» провайдерах IP рано или поздно может попасть под раздачу — РКН расширяет списки постоянно. Самое надёжное долгосрочное решение — спрятать VPN-серверы за CDN:

- Вместо голого IP + Reality → **VLESS + WS (или gRPC) + настоящий TLS** через домен, проксируемый через Cloudflare (orange cloud)
- Клиент видит edge Cloudflare, а не IP наших серверов — заблокировать весь Cloudflare никто не станет (это половина интернета)
- Для этого нужно: домен на Cloudflare (можно поддомен tuvpn.ru, но текущий tuvpn.ru сейчас НЕ на Cloudflare — NS: ns1-4.adminvps.ru/net; либо заводить отдельный домен под это, либо мигрировать NS tuvpn.ru целиком) + доступ к Cloudflare-аккаунту + переделка инбаундов в x-ui под WS/gRPC + правки `subscription_generator.py`
- Это НЕ горит прямо сейчас, можно сделать после переезда на новые серверы, как страховку на будущее
